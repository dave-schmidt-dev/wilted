## Outcome

The Mac remains the canonical episode-state owner; iOS becomes a listening client that actually receives everything the Mac publishes, keeps the newest state it or the server has for a given record instead of racing itself, durably records how far the user got, drives the lock screen and headphones for real, downloads only what playback needs, and tells the Mac about listening changes without a manual button press. Podcast episodes — currently unable to ever reach an iPhone — become sync-eligible content, in a way that does not multiply the number of CloudKit schema bumps this work requires beyond two (Phase 2, and possibly Phase 3 riding the same bump — see that phase). No CarPlay or car-specific work.

## Findings, current evidence, and disposition

Findings are grouped by the phase that fixes them; each retains its original review number for traceability.

**Sync-integrity core (findings 2, 3, 4, 12) — `ListenerRepository` commit/acknowledge/rebuild**

- **#2**, `Listener/Sources/WiltedListener/ListenerRepository.swift:140` (`commit`): `for record in catalogRecords { records[record.id] = record }` — unconditional overwrite by record ID, no check against a newer local value. The identical pattern exists on the Mac side: `Producer/Sources/WiltedProducer/LocalLibrarySyncRepository.swift`'s `mergedState` (`for fetched in batch.records { records.removeAll {...}; records.append(fetched) }`) installs fetched records with no guard either, though its surrounding function does already use `protectedRecordIDs`/pending-ID sets to guard *deletions* — the same sets are simply never consulted for *installs*. Confirmed by direct read on both platforms.
- **#3**, `ListenerRepository.swift:227,239` (`acknowledge`): pending-queue filtering and server-envelope installation both match by record ID alone (`current.pendingChanges.first(where: { $0.recordID == id })`). Because `enqueue()` replaces (not appends) any existing pending entry for a given record ID (`ListenerRepository.swift:155`, `pending.filter { $0.recordID != change.recordID }` then append), there is only ever one queued entry per ID — so an ack for an in-flight send of checkpoint N, arriving after a newer checkpoint N+1 was enqueued for the same ID while N was still in flight, matches and deletes N+1's queue entry (never sent) and installs N's stale server echo over the newer local record. Confirmed by direct read. Mac's `LocalLibrarySyncRepository.acknowledge` has the same by-ID-only match (`pending.removeAll { $0.recordID == recordID }`, then installs `result.serverEnvelopes` unconditionally) — same defect, confirmed by direct read.
- **#4**, `WiltediOS/ListenerAppModel.swift:726-803` (`rebuild`): collapses revisions/playback via `commit`'s alphabetical-by-record-ID ordering, not revision recency; `play()` (`:494-521`) never checks a cached playback record's `revisionID` against the selected audio revision. Contradicts this repo's own `INVARIANTS.md:102` ("a superseded revision's outcome never masks the current one") — the Mac side already solved this class of bug for preparation outcomes; iOS never inherited it for playback records.
- **#12**, `CloudSync/Sources/WiltedCloudKit/CloudKitSyncTransport.swift:250-253` (corrected path — this file lives in the separate `CloudSync` Swift package, not under `Listener/Sources/WiltedListener/` as originally cited): the shared engine cursor advances from `.stateUpdated` before `ListenerRepository.commit` of the corresponding batch succeeds. If that commit later fails (realistic: the existing `staleStage` guard can fire from an ordinary concurrent `enqueue()` racing a refresh), the advanced cursor persists on the next send/ack and the uncommitted batch is skipped until the server changes again.

**Correction to this plan's first draft — the fix is not a `sequence` comparison.** The first draft of this plan proposed guarding `commit`/`acknowledge` with `PlaybackState.sequence`. An external contrarian review (and independent re-verification against source) found this premise false: `sequence` resets to `1` on every new playback session — `WiltediOS/ListenerAppModel.swift:874` (`makeInitialPlayback`) and `:833`/`nextPlayback`'s `sequence: newSession ? 1 : current.sequence + 1`, and `explicitPositionChange` (`:849`, used for every rewind/forward/scrub) always passes `newSession: true`. An ordinary seek resets local sequence to 1 while the shared CloudKit record may hold a far higher value from a prior session, so a raw `sequence >=` comparison would itself cause exactly the data loss (or the reverse: permanent one-way rejection) Phase 1 exists to prevent. `sequence` also exists only on `.playbackState` records (`WiltedRecordCodec.swift:287,308,313,338` — absent from every other record type's known-field list), so it cannot govern `commit`'s overwrite loop for `.item`/`.revision`/`.transcript` records regardless. **The corrected fix needs no CloudKit schema and no new field at all** — see Phase 1 below for the actual mechanism, which reuses `protectedRecordIDs` (already populated on every `enqueue`, already `WiltedRecordID`-generic) and the pending change's own `Equatable` identity captured at send time.

**Finding 12's fix is not cursor-timing either.** A domain-specialist review raised, and this planning pass agrees, that `CKSyncEngine`'s own internal cursor advances the moment `.stateUpdate` fires in `handleEvent` — independent of whether the app later persists that serialization to disk. Deferring *our* on-disk persistence (which, per `ListenerRepository.commit`, already only happens as part of a successful `commit`'s `persist(next)` call — the durable half of finding 12 is arguably already correct) does not stop the live, still-running `CKSyncEngine` instance from having already discarded the batch internally; only a relaunch (fresh engine built from the old on-disk serialization) would re-deliver it. The actual gap is that `SyncCoordinator.synchronize()` (`WiltedKit/Sources/WiltedSync/SyncCoordinator.swift:17-32`) does not retry `stage`/`commit` when `commit` throws `staleStage` — it already holds the fetched `batch` in memory at that point and simply discards it on error. See Phase 1 below. Separately (domain-specialist, round 2): when `synchronize()`'s bounded retry is itself exhausted, or a non-`staleStage` error terminates it, the live `CKSyncEngine` instance can be left in a state that keeps failing identically on every subsequent call — `CloudSync/Sources/WiltedCloudKit/CloudKitSyncTransport.swift:248-253,319` and `SyncCoordinator.swift:150-155` show no path that rebuilds the engine after a hard failure. Phase 1 adds a bounded rebuild-the-engine-and-retry-once step for this case (Amber, not a Red decision — there is one clearly correct behavior: rebuild from last-known-good persisted state and retry, same as a fresh cold launch would).

**Round 2 finding this plan does not adopt: an `updatedAt` tie-break for finding 4.** The first correction (above) proposed `updatedAt` as a tie-break when `article.currentRevisionID` membership does not fully disambiguate. A contrarian review (round 2) correctly flagged that `updatedAt` is a wall-clock field and this repo's own `INVARIANTS.md:98-102` (W-INV-011) states timestamps must never outrank session/sequence for playback state — an `updatedAt` tie-break would silently reintroduce the clock-skew class of bug Phase 1 exists to close. **Resolved by removing `updatedAt` from finding 4's mechanism entirely**, not by refining it: revision selection uses `currentRevisionID` membership only (no tie-break needed — `WiltedRecordID.playback(_:_:)` is keyed by `(itemID, revisionID)`, so at most one playback record can match the current revision; a stale record for a superseded revision fails the membership check outright and is never a candidate). Playback *value* resolution across sessions/devices for the current revision is handled by `mergePlayback` (see the corrected Phase 1 mechanism below), which is causally gated (session, sequence, intent), never timestamp-gated. W-INV-011's own text is itself scoped to `PlaybackState` (revision-keyed, `mergePlayback`'s existing contract) versus the *not-yet-synced* item-keyed `PodcastListeningRecord`/`PodcastPreparationOutcomeRecord` (`LocalLibrarySchemaV10Models`, `INVARIANTS.md:98-102`) — a contrarian finding treated these as one contradiction; they are two different records with two different (compatible, not conflicting) merge rules. Phase 2 must name both local-only record types explicitly and state that neither is sync-eligible under this plan; if either becomes sync-eligible later, `PodcastListeningRecord`'s own item-scoped last-writer-wins-by-`updatedAt` rule (already specified in INVARIANTS.md) is unrelated to and does not conflict with `mergePlayback`'s revision-scoped causal rule.

**Major discovery this planning pass, confirmed by direct read, changing the "port to iOS" framing entirely.** `WiltedKit/Sources/WiltedDomain/PlaybackMerge.swift`'s `mergePlayback(current:incoming:changeTagMatches:)` is an existing, fully tested (`contracts/fixtures/*.json`, `scripts/validate-contract-fixtures.swift`, `WiltedDomainTests`), causally-correct LWW merge function for `PlaybackState` — it already solves the exact cross-session `sequence`-reset problem the first correction above (finding 12/CR-1) identifies, by requiring an explicit `.rewind`/`.restart` intent (not just a higher raw `sequence`) for any cross-session acceptance. **It is never called from either platform's `SyncRepository` commit/acknowledge layer** — `applyRemote` (`Listener/Sources/WiltedListener/Playback.swift:153-159`), its only production caller, operates on the live in-memory playback engine, not on `ListenerRepository.commit`/`ListenerAppModel.rebuild`. This means finding 2/3's fix for `.playbackState` records specifically should not be the generic `protectedRecordIDs`/pending-ID-set guard described in the original correction above — it should route through `mergePlayback`, the existing tested contract, instead of inventing a third ad-hoc mechanism. `applyRemote`'s live-in-memory-engine use of `mergePlayback` is a separate, already-working concern and stays out of this plan's scope (added to Exclusions).

**The Mac already has a partial version of this fix — and it has its own, previously-undiscovered bug.** `Producer/Sources/WiltedProducer/LocalLibraryStore.swift:2822-2841` (`applySyncCommit`'s `commit.playbacks` loop) already calls `mergePlayback` when applying a fetched playback record onto its SwiftData row, and refreshes the row's stored CloudKit system-fields/changeTag from the incoming record when `merge.acceptedStateIsIncoming`. Two problems, both confirmed by direct read, neither found by either review round:

1. **The sidecar refresh is conditional on the merge's winner** (`LocalLibraryStore.swift:2837`, `guard merge.acceptedStateIsIncoming else { continue }`) — when the local value wins (a legitimate, expected outcome, not an error case), the row's stored system fields/changeTag are never updated to the just-fetched server version. This is DS-1/R2-CR-6/R2-CR-7's finding, but it is a live bug in the Mac's own shipped code, not just a gap iOS needs to avoid inheriting.
2. **New finding, not from either review round — `changeTagMatches` is very likely computed backwards for the ordinary cross-device case.** `LocalLibraryStore.swift:2833-2835` computes it as `existing.encodedCloudKitRecordChangeTag == applied.sidecar.changeTag` — the row's *previously stored* tag against the *just-fetched* tag. `contracts/fixtures/02-forward-progress.json` (the fixture-verified contract for this exact function) requires `changeTagMatches: true` for its "ordinary progress advances... with a newer sequence" case — the routine cross-device scenario `mergePlayback` exists to accept. But every genuine CloudKit write produces a *new* `recordChangeTag`; a locally stored tag from before that write will essentially never equal the freshly fetched tag after a real remote update. Combined with problem 1 (sidecar refreshes only on accept), a record can permanently wedge into rejecting all future updates the first time this mismatch fires, since nothing ever refreshes the stored tag to let a later comparison succeed. No fixture or test exercises the `staleChangeTag` rejection path or a differing-tag cross-device scenario, so this shipped without a regression-catching test. This is a plausible, currently-live defect in already-shipped Mac production code, found only by directly cross-referencing the fixture contract against the call site — not part of either review round's findings, and not yet independently confirmed by a runtime repro.

**Podcast CloudKit schema (finding 1)**

- **#1**, CONFIRMED AND DEEPER THAN ORIGINALLY REPORTED. `WiltedKit/Sources/WiltedSync/RecordTypes.swift`'s `WiltedRecordType` has exactly five cases — `.item`, `.revision`, `.revisionChunk`, `.transcript`, `.playbackState` — no podcast feed/episode record type exists at all. `WiltedRecordCodec.swift`'s `.item` encode/decode (lines 1-75) is Article-shaped only: fields are `itemID`/`canonicalURL`/`title`/`source`/`createdAt`/`isDeleted`/`schemaVersion`/`currentRevisionID`, identity validated via `ItemID.derive(from:)` — distinct from `ItemID.derivePodcastEpisode(feedURL:rssGUID:enclosureURL:)` used elsewhere for podcasts. `WiltedMacModel.swift:4140-4151` (`queuePreparedPublication`), `:4165-4186` (`queueUnpublishedReadyRevisions`), `:4188-4201` (`queueCurrentPlaybackCheckpoint`) all require Article/`store.articles()` membership, and podcast preparation's completion handler (`:2420-2445`) never calls any publication-queue function — confirmed directly by reading the full handler; it calls `loadLibrary`, `applyEpisodes`, `reloadPreparedPlayback`, `refreshProcessorRuns`, nothing sync-related. A fully processed podcast episode cannot reach an iPhone today, full stop. This is a missing CloudKit schema, not a missing enumeration call.

  **Two corrections to this plan's first draft, both confirmed by direct read:**
  - `WiltedRecordType` is switched over exhaustively (no `default` case) in at least seven places, not the handful this plan's first draft named: `Producer/Sources/WiltedProducer/LocalLibrarySyncRepository.swift`, `Producer/Sources/WiltedProducer/LocalLibraryStore.swift`, `Listener/Sources/WiltedListener/ListenerRepository.swift`, `WiltedKit/Sources/WiltedSync/WiltedRecordCodec.swift`, `CloudSync/Sources/WiltedCloudKit/CloudKitRecordMapper.swift`, `CloudSync/Sources/WiltedCloudKit/CloudKitSyncTransport.swift`, `WiltediOS/ListenerAppModel.swift`. A new case breaks compilation in all seven; Phase 2's task must touch all of them (the first draft's task file omitted several).
  - The Mac-side publication path is not `WiltedMacModel`'s queue functions directly — they delegate to `WiltedMac/Sync/WiltedMacSyncLifecycle.swift`'s `queueItem(_ article: Article, ...)` (`:140`), `queueRevision(_ revision: AudioRevision, ...)` (`:149`, `:162`), and `queuePlayback(_ state: PlaybackState, ...)` (`:188`) — all statically typed to `Article`/`AudioRevision`/`PlaybackState`, none of which can carry a podcast episode without new, podcast-typed lifecycle functions alongside the existing ones. `WiltedMacModel.swift`'s queue functions must extend to call the new functions for podcast episodes, not just enumerate them.

  **A return-path gap not in the original 22 findings, surfaced during this planning pass:** `queuePlayback` takes a `PlaybackState`, and `PlaybackState.itemReference` must resolve to an `.item` record on both ends. If the Mac's inbound playback-acknowledgement path looks up the referenced item via `store.articles()` the same way the outbound queue functions do, then a playback checkpoint for a podcast episode sent *from* iOS would be silently unresolvable on the Mac even after Phase 2 ships outbound publication — the fix must cover the Mac's inbound path for podcast playback records, not only the outbound publication direction. Verify `WiltedMacSyncLifecycle`'s playback-receipt handling against podcast item lookup before scoping Task 2.2 as publication-only.

**On-demand asset transfer for chunked audio (finding 13)**

- **#13**. Review-time status was NEEDS-RUNTIME-EVIDENCE. This planning pass queried current Apple documentation (context7, `/websites/developer_apple_cloudkit`): `CKFetchRecordZoneChangesOperation.ZoneOptions.desiredKeys` — "If the property is set to nil, which is the default, CloudKit fetches all available keys for the records" (i.e. full field data, including `CKAsset` fields, transfers during an ordinary change fetch unless the caller explicitly restricts keys). `CKSyncEngine.FetchChangesOptions` — the only fetch-configuration surface `CKSyncEngine` exposes to callers — has no `desiredKeys` equivalent; it exposes `operationGroup`, `prioritizedZoneIDs`, and `scope`, nothing field-level. Since `.revisionChunk` records (which carry the actual `CKAsset` audio payload) live in the same zone as everything else the app syncs, an ordinary `CKSyncEngine.fetchChanges()` — the operation this app's "metadata-only refresh" runs — has no configuration path to exclude chunk asset bytes from that fetch. **Upgraded to CONFIRMED (by current Apple documentation, not yet by an instrumented trace).** Phase 3 below carries one bounded network-trace task to close the residual gap between "the API offers no way to prevent this" and "CloudKit definitely does transfer the bytes eagerly in practice" before committing to the architectural fix.

**Legacy asset back-compat (finding 11)**

- **#11**, narrow and conditional. The legacy single-`CKAsset` (non-chunked) revision production write path (`WiltedMacSyncLifecycle.queueRevision(_:audioAsset:)`) is confirmed dead in current Mac production code — test-only; the one production call site uses the chunked variant — so this cannot happen to newly-processed episodes going forward. The iOS decode fallback for that legacy shape is still reachable for pre-existing CloudKit records from before the chunked migration: `ListenerAppModel.swift:941-949`'s `assetLoader` for that shape checks `transport.assetHandoff()`/`mapper.resolvedAssetURL` and then throws — neither fetches bytes by record identity. Net effect: an existing user's old single-asset episodes become permanently undownloadable after a clean reinstall. Scoped as a migration/back-compat fix.

**Durable playback completion (finding 5)**

- **#5**. `Listener/Sources/WiltedListener/Playback.swift`'s `AVFoundationAudioEngine` (16-28) has no completion delegate/callback at all — the Mac's `PlaybackController` already has one; it was never ported. Every constructed state uses `completed: false`. `liveReadout` (164-188) is deliberately non-durable/UI-only — documented, accepted tradeoff, avoids a per-second durable write, not part of this finding. Selecting a new item never persists the outgoing item's live position first. Net: natural episode completion, extended backgrounding, and switching items without pausing can all lose durable listening progress.

**Remote command lifecycle (findings 6, 7) — independent bugs, same UI surface**

- **#6**. `WiltediOS/WiltediOSApp.swift:~102` installs a throwaway `MediaPlayerRemoteCommands()` with no stored strong reference anywhere; its closures capture `[weak self]`, so ARC can deallocate it almost immediately, silently no-opping every lock-screen/headphone command while still reporting `.success`. `ListenerTests.swift` holds its test double directly and never exercises the real `MPRemoteCommandCenter` + weak-self production path — zero coverage today.
- **#7**, independent of #6. Even with the command object retained, `handleRemote`/`advanceRemote` (`Playback.swift:209-239`) update engine/controller state and Now Playing, then emit into the controller's own status stream, which `ListenerAppModel.observePlayback` (`:986-990`) drains and discards (`for await _ in stream {}`). A remote pause/rewind never reaches `recordPlayback` or published model state.

**Sync/playback status conflation (finding 8)**

- **#8**. `model.status` is one enum for both sync-operation phase and playback phase. `ListenerAppView.swift` derives Play/Pause solely from `status == .playing`; `refresh()`, `download()`, `sendPending()`, and generic repository/transport event handling all unconditionally overwrite `status` to non-playing values while audio may still be playing — desyncing transport UI and the live position readout (also gated on `status == .playing`) from actual engine state.

**Automatic send-back (finding 9)**

- **#9**. No automatic send-back of listening changes exists anywhere in the iOS app: `recordPlayback` only enqueues locally; the live CloudKit driver uses `automaticallySync: false`; the only call site of `sendPending()` in the whole app is a manual Settings button; foreground/resume only triggers refresh (pull), never send (push). The Mac side already has an automatic sender that retriggers on foreground/startup — iOS never got the equivalent. In-app copy claims changes "will send when connected," which is false today.

**Cold-launch fallback gap (finding 10)**

- **#10**. `ListenerAppModel.swift:310-341`: a thrown error during live CloudKit session construction on cold launch returns immediately without ever loading the local repository/catalog — contrast the later post-fetch failure path at `:375-387`, which does fall back to `loadLocal`. A corrupted/incompatible persisted `CKSyncEngine` serialization can hide an otherwise-valid offline library and downloaded audio indefinitely, with retries repeating the same failure.

**Download/cache lifecycle hygiene (findings 15, 16, 17, 18, 19)**

- **#15**. `sendPending()` never calls `updateDownloadedStates()` after acknowledgement, so `rebuild()`'s default `.metadataOnly` classification makes a fully-cached, playable item appear undownloaded until an unrelated operation reconciles cache state.
- **#16**. Canceling a selected-audio download only cancels CKSyncEngine-level operations; the `database.records(for:)` fetch behind selected-audio download has no stored cancellation token and keeps running/consuming bandwidth after cancel.
- **#17**. Replacing an item's ready revision leaves the old revision's downloaded audio file on disk with no reachable mapping to remove it — orphan-tracking is ItemID-level, not revision-level; storage leaks silently across reprocessing.
- **#18**. Cache storage is purely content-hash-keyed with no reference counting; removing one item's download can delete a file another item with identical audio bytes still depends on, breaking that sibling item's playback until later reconciliation.
- **#19**. Every availability/refresh reconciliation and every playback start does a full-file read + SHA-256 hash of the relevant cached audio file(s), with no incremental/cheap validation path. Cost scales with total cached library size on every routine refresh. Existence confirmed; severity needs a runtime measurement (this phase's gate includes one).

**UI correctness (findings 20, 21, 22)**

- **#20**. The single Retry button always calls `refresh()` regardless of which operation actually failed (download, send, playback, seek) — can silently paper over a still-broken operation.
- **#21**. The single-active-operation guard (`beginOperation`) silently drops additional download taps with no queuing, rejection feedback, or automatic retry once the in-flight operation completes; no busy-state feedback on the Download button (contrast Refresh, which does disable while busy).
- **#22**. Seeking (rewind/forward/scrub) always calls `playback.play()` with no paused-vs-playing branch and no "reposition without playing" state in the playback-intent model — adjusting position while paused audibly starts playback. No test or comment suggests this was deliberate.

**Deliberate tradeoff, copy-only (finding 14)**

- **#14**. `ListenerRepository.quarantineAfterAccountChange` drops pending changes on purpose — `HISTORY.md:860` explicitly documents this as accepted ("playback state belongs to the account that produced it and is cheap to re-derive... a durable quarantine restore on the listener would therefore be unreachable code"). The only real gap: `Shared/WiltedRootView.swift:103` ("kept your local work") is imprecise for the listener specifically, since catalog records are kept but unsent playback progress is not. Not a logic fix — gated on confirming the product intent still holds.

  **Correction to this plan's first draft:** that copy string (`WiltedScreenCopy.useCurrentAccountDetail`) is not listener-specific — it is defined once in `Shared/WiltedRootView.swift` and consumed by both platforms via `Shared/WiltedSurfaces.swift`. Confirmed by direct read that the two platforms' quarantine behavior actually differs: Mac's `LocalLibrarySyncRepository.quarantineAfterAccountChange` (`Producer/Sources/WiltedProducer/LocalLibrarySyncRepository.swift:48`) durably conflicts and protects pending changes rather than dropping them — "kept your local work" is *true* for Mac today. Editing the shared string to be accurate for iOS (which does drop unsent playback progress) risks making it newly inaccurate for Mac. Fixing this requires either wording that is honest on both platforms, or splitting the string per-platform (a small code change, not a pure copy edit). See Red decision 3.

## Red decisions for explicit owner sign-off

These are batched into one packet per the standing lifecycle rule (no stream of individual questions). Each has a recommended default; implementation of the phase in parentheses is blocked until the decision is made.

**Owner disposition, 2026-09-13 (after round 3 of adversarial review):** decisions 1-3 are approved at their stated recommended defaults, below. Decision 4 is **not approved** — after three independent adversarial-review rounds against successive designs plus a fourth round (round 3) that found *more* high-severity defects than round 2 against an already-corrected mechanism, the `.playbackState` sync mechanism is sent back for a fresh design pass rather than another patch iteration. See "Round 3 outcome and Phase 1 disposition" below. Phases 2-4 and 9-13 proceed on the strength of decisions 1-3's approval. Phase 1's non-`.playbackState` tasks (1.0, 1.1, 1.2, 1.3, 1.4, 1.5) also proceed — they were not implicated by the redesign decision — but see that same section for task-file contract corrections applied before dispatch.

1. **Podcast CloudKit record-type shape (Phase 2).** Recommended default: new dedicated record types (`.podcastFeed`, `.podcastEpisode`, `.podcastEpisodeChunk` or equivalent), mirroring the existing item/revision/revisionChunk separation, with identity derived via the existing `ItemID.derivePodcastEpisode(feedURL:rssGUID:enclosureURL:)`. Alternative considered and not recommended: generalize `.item`/`.revision` with a content-type discriminator field — fewer new record types, but couples Article and podcast identity/decode logic that are already intentionally separate (`ItemID.derive` vs. `ItemID.derivePodcastEpisode`), and would require every existing `.item`/`.revision` consumer to branch on content type. Recommendation: dedicated types. **This decision must also state whether `.playbackState.itemReference` can reference a podcast-episode record without a `WiltedRecordCodec`/`CloudKitRecordMapper` change** — the answer determines whether Task 2.2's Mac-inbound-playback gap (noted above) is free or requires its own codec work. **Also state explicitly (round 2 finding) whether `PodcastListeningRecord`/`PodcastPreparationOutcomeRecord` (`LocalLibrarySchemaV10Models`, local-only today per `INVARIANTS.md:98-102`) become sync-eligible under this phase.** Recommended default: no — neither is in scope; this plan only makes podcast *episodes* (the catalog/audio content) sync-eligible, not the local-only listening-completion/preparation-outcome records. If a future phase makes them sync-eligible, `PodcastListeningRecord` needs its own item-scoped last-writer-wins-by-`updatedAt` merge rule (already specified in INVARIANTS.md, distinct from and compatible with `mergePlayback`'s revision-scoped causal rule) — not something this plan needs to design now.
2. **CloudKit zone layout for on-demand asset transfer (Phase 3, depends on #1's outcome).** Recommended default: move `.revisionChunk` (and, if #1 lands, its podcast equivalent) into a CloudKit record zone that is excluded from `CKSyncEngine`'s tracked/prioritized zones, fetched only via a direct `CKDatabase.records(for:)` lookup by record ID at actual download time. Alternative: accept the eager transfer as a known cost and only fix it if the network trace (this phase's first task) shows it is actually significant in practice. Recommendation: do the trace first; only commit to zone-splitting if the trace confirms real byte transfer, since zone-splitting is the more invasive of the two and should not be paid for on a documentation inference alone. **Correction (round 2 contrarian, confirmed by direct read): this decision is understated as an "excluded zone" description.** `WiltedRecordID`'s `Hashable`/identity includes `zoneName` (`WiltedKit/Sources/WiltedSync/RecordTypes.swift:14-26`, `guard zoneName == "WiltedZone"` in `init`), and `CKRecord.Reference` cannot cross zones — so splitting `.revisionChunk` into a second zone (a) re-identifies every persisted `WiltedRecordID`-keyed guard-set entry that references a chunk record (`protectedRecordIDs`, `conflictedRecordIDs`, pending-change record IDs), and (b) requires a non-`CKRecord.Reference` mechanism for a chunk record to reference its parent revision, since a same-zone `Reference` field can't point across the split. This is a redesign of the parent-identity mechanism, not a zone-attribute flip. Fold the "is a second zone even fetchable through the same `CKSyncEngine` instance at all" question into Phase 3's Task 3.1 network-trace spike (it needs an answer before zone-splitting can even be attempted, not just before it's judged worthwhile) and keep the recommended default as no-split pending that spike's result — the added redesign cost strengthens, not weakens, the case for proving the eager-transfer cost is real before committing to it.
3. **Finding 14 copy scope (Phase 12).** The shared copy string is confirmed accurate for Mac and inaccurate for iOS (Mac's quarantine durably protects pending changes; iOS's drops them — see finding 14 disposition above). Recommended default: reword to a single platform-neutral sentence true on both ("Wilted paused sync. ### Shared-file serialization (added, round 5 outcome, CR-4/CR-6; revised, round 6 outcome, CR-1/DS-1; corrected, round 7 outcome, CR-1/DS-1/CR-6)

Three consecutive review rounds (3, 4, 5) each found an unordered shared-file overlap the prior round's fix had just created or missed, always inside Phase 1. Round 5's exhaustive whole-plan re-run of the same overlap check showed the problem was never Phase-1-local — it is systemic to how many tasks in this plan touch a small number of hub files (`WiltediOS/ListenerAppModel.swift`: 14 tasks across 8 phases; `Listener/Tests/WiltedListenerTests/ListenerTests.swift`: 9 tasks across 6 phases; `WiltediOSTests/ListenerAppModelTests.swift`: 12 tasks across 7 phases; plus smaller cross-phase sets on `SyncCoordinator.swift`, `SyncSmokeTests.swift`, `WiltedMacSyncLifecycle.swift`, and several `CloudSync` files). Enumerating this as explicit pairwise `Blocked by` edges is both what the last three rounds attempted in miniature and unmaintainable at the scale the exhaustive check reveals (~150+ pairs). The rule replacing that approach is now two separate rules, previously conflated into one predicate (round 7 correction — see below):

1. **Mutual exclusion (no predicate):** Switchyard never dispatches two tasks concurrently whose `Files` lists intersect, full stop, regardless of Status, `External blockers`, phase, or explicit `Blocked by` presence/absence. This is what actually prevents the concurrent-overwrite class; it has no exemption to get wrong.
2. **Ordering:** among tasks sharing a `Files` entry that are not yet landed and not held, the lower numeric task ID (ordered by ascending numeric task ID — `1.0 < 1.1 < ... < 13.1` — not the physical heading order of the task file, which is not numerically ascending) is the implicit predecessor, in addition to any explicit `Blocked by` list the task file states. A lower-numbered sharer is exempt from being an implicit predecessor only if its Status is exactly `done` (already landed, no longer in flight) or it has an `External blockers` entry (cannot be in flight) — every other Status, including `in progress` and any unrecognized value, still counts as blocking. **An `External blockers` entry is present only while its blocker is unresolved: the line is deleted from the task the moment the blocker clears, never left in place with a note like "resolved"** (round 8 outcome, CR-1) — **and for a blocker slug naming a plan-internal resolver task, this is a dispatch-time check, not just a documented convention** (adjudicator AJ-1: round 8's documentation-only fix was ruled fix-inadequate, since nothing stopped a stale line from surviving past actual resolution). A task's Done-when may declare `Resolves external blocker: <slug>`; `/tmp/plan-review-prompts/overlap-check.py`'s `check_blocker_resolution` fails if that resolver task is `done` while another task still carries an `External blockers:` line for the same slug. A blocker with no plan-internal resolver (a live-account condition, a future cross-run redesign) has no task whose completion can mechanically prove resolution, so presence remains the only signal there — an unavoidable residual, not an oversight.

**Round 7 correction (CR-1/DS-1):** round 6 introduced the exemption without splitting rules 1 and 2 above, and its Status conjunct read "Status is not pending" rather than "Status is done" — which incorrectly also exempted `in progress` (an actively in-flight task) from serializing its dependents, permitting exactly the concurrent same-file dispatch this rule exists to prevent, independently confirmed by both round 7 reviewers with an empirical repro (flipping a task's Status to `in progress` and showing the overlap script wrongly treated it as exempt). Splitting mutual exclusion (rule 1, no predicate) from ordering (rule 2, where the predicate lives) means a future predicate bug in rule 2 can no longer reopen the concurrency hole rule 1 closes on its own. When an externally-blocked task's blocker clears and it re-enters the dispatch pool, its own dispatch re-verifies against then-current Files under the revert-and-reconfirm discipline this plan already requires, so the exemption defers the ordering check rather than skipping it. This is verifiable mechanically via `/tmp/plan-review-prompts/overlap-check.py` (or its successor), which exits non-zero on an explicit `Blocked by` list naming a higher-numbered task (a genuine cycle against the implicit rule; there are none currently) and reports — without failing on — an exempt lower-numbered owner, which is allowed by design. Task authors do not need to compute or write pairwise edges by hand; the canonical task-number order plus this rule does that implicitly.

**Every cross-phase dependency stated in this Ordering section's prose gets an explicit `Blocked by` edge; the implicit file-sharing rule above is hygiene, never the sole carrier of a semantic dependency** (round 7 correction, CR-6: round 6's exemption silently dropped the implicit 3.2→8.1 edge that had been accidentally enforcing this section's then-stated "Phase 8 also depends on Phase 3's outcome" prose constraint, leaving it enforced only by prose no dispatch-time check reads; adjudicator AJ-2 correction, round 8: fixed the edge's conditionality by redefining Task 3.2's Done-when to always reach a terminal `done` state, rather than inventing conditional-edge syntax). **This dependency was removed entirely in round 9 (premortem SR-2 correction)**, once source verification showed Task 8.1's actual design never triggers the automatic-fetch risk the dependency existed to guard against — see "Phase 8" above and Round 9's outcome section for the corrected reasoning. Rounds 7-8's fixes to the edge's *mechanics* (making it explicit, then making it unconditional) were sound work on a dependency that round 9 found should not have existed in the first place; both remain correct examples of "give every cross-phase dependency an explicit edge" for the dependencies that do hold, such as Task 2.2's `Blocked by: 1.0` (added round 9 for the PM-6 fix, same convention).

**Gate-grep protection (added, round 6 outcome, CR-2; corrected, round 7 outcome, CR-2/CR-3; round 8 outcome, CR-4; corrected again, adjudicator AJ-3):** `scripts/test-gate.sh` makes two kinds of literal-match assertion against a fixed path — `grep -Fq`, `grep -Eq`, `grep -Fxq`, and `grep -Fxc` all appear; `grep -n "grep -[EF]xq\|grep -[EF]q\|grep -Fxc" scripts/test-gate.sh` finds every such line, then exclude any whose target is a shell variable (a generated log or an enumerated artifact list, e.g. `:205,259,266,267`) rather than a literal path — the seven files below are what remains: (a) log-based — asserted against a `$tmp_root/*.xctest.log` produced by actually running a gate leg (CloudSync leg `:444,448`, Listener leg `:471,475`, WiltedKit leg `:713,715,717`), against `CloudSync/Tests/WiltedCloudKitTests/CloudKitAdapterTests.swift`, `Listener/Tests/WiltedListenerTests/ListenerTests.swift`, and `WiltedKit/Tests/WiltedSyncTests/SyncSmokeTests.swift`; (b) source-based — directly against a shipping source file: `WiltedMac/WiltedMacRootView.swift`, `Shared/WiltedRootView.swift`, `WiltediOS/ListenerAppView.swift`, `WiltedMacTests/WiltedPixelSnapshotTests.swift`, `WiltedMacTests/WiltedVisualSystemTests.swift`, `WiltedMacUITests/WiltedMacSmokeUITests.swift`, `WiltediOSUITests/WiltediOSPixelSnapshotTests.swift`.

**Adjudicator AJ-3 correction:** round 8's CR-3 was ruled fix-inadequate — "re-run the actual gate leg for the touched package" is not an operation `scripts/test-gate.sh` supports without a full nine-leg run, and no task's Quick checks or Done-when ever invoked it.
